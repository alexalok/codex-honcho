# Cross-chat delegation capture

## Supported delivery shapes

The parser recognizes these rollout `response_item` payloads:

- Modern delivery: an unpaired `function_call_output` with `namespace: "codex_app"`, `name: "send_message_to_thread"`, and a `codex_delegation` envelope in `output`. Output may be a string or Responses `input_text` blocks. A missing or null `call_id` identifies this as injected input rather than a result paired with an outgoing call.
- Compatibility delivery: a `message` with `role: "user"` and a standalone `codex_delegation` envelope in its text. Human text around complete envelopes retains human attribution. Inline prose, fenced examples, blockquotes and assistant quotations are preserved as ordinary conversation.

The desktop envelope has this form:

```xml
<codex_delegation><source_thread_id>11111111-1111-4111-8111-111111111111</source_thread_id><input>Inspect the fixture &amp; report results.</input></codex_delegation>
```

The source ID must be a UUID. The desktop's `&amp;`, `&lt;` and `&gt;` escapes are decoded once; escaped markup stays task text. Recognized malformed envelopes are retained verbatim as unknown agent-origin input. A malformed envelope consumes the remaining segment conservatively, because its closing boundary cannot be trusted. Arbitrary shell/MCP/custom-tool results, outputs from other tools and delivery output without an envelope remain excluded. Existing injected-context filtering runs before compatibility parsing; decoded delegated text is not reinterpreted as injected context.

These are transport classifications, not authentication. A human can supply an envelope-shaped message, and a claimed source ID can name an existing thread. Neither the wrapper nor a matching identity record grants permission or makes the task authoritative.

## Attribution and replay

`SessionStart` and writeback record their own resolved `aiPeer` and `sessionName` locally. This uses the existing root/`hosts.codex`/`globalOverride` configuration precedence and session strategies. Records are indexed by exact Codex thread ID and scoped to the Honcho endpoint and workspace. The index contains no API keys. Conflicting observations disable resolution for that thread instead of overwriting its historical identity. Existing conversations acquire records only when a new hook observes them; no old transcripts or other accounts' homes are searched.

Capture snapshots any resolved sender in the queue, bound to its endpoint/workspace scope. Unknown senders remain unknown on retry, and a snapshot cannot identify a named peer after the upload destination changes. During upload, delegated tasks go to the resolved AI peer or the explicit `codex-delegation-unknown` peer (`observeMe: false`); the fallback avoids collisions with the configured human and receiving AI. The human peer is never an eligible delegation sender.

Every uploaded part has structured metadata: `type: "delegation"`, `origin: "agent"`, `provenance_scope: "routing"`, transport, wrapper validity, source thread ID, sender resolution, source peer and configured source session name. There are no inferred peer names or permission labels in the task text. Normal human, assistant and tool-observation messages keep their existing attribution and formatting.

The new `rollout-items-v2` cursor counts source items, so splitting a mixed message does not shift later captures. A legacy count is translated to the end of the same previously captured message. Earlier tool deliveries are not backfilled; subsequent deliveries are captured. Repeated capture is incremental, and a shortened transcript retains the existing reset-and-replay behavior. Identical task text in distinct deliveries remains distinct.

Legacy pending user-wrapper entries are normalized during upload without rewriting their queue or moving the sent marker past unsent entries. Already uploaded messages and conclusions are untouched. Chunking, the 100-message batch limit and the existing 100-part per-entry overflow limit remain in effect. Queue/cursor writes and remote delivery retain the existing failure semantics; this change does not introduce an exactly-once network protocol.

## Fixture verification

The synthetic helpers in `test/fixtures/delegation.ts` contain no live messages or conclusions. Supported modern field and content shapes were checked against JSON schemas generated by the installed Codex CLI 0.164.0:

```sh
codex app-server generate-json-schema --experimental --out /tmp/codex-delegation-schema
```

The relevant definitions are `TurnStartParams` (`TurnToolOutput`, `FunctionCallOutputBody`) and `RawResponseItemCompletedNotification` (`FunctionCallOutputResponseItem`). The desktop wrapper follows its verified `sourceThreadId`/escaped-input contract. See the [official app-server documentation](https://developers.openai.com/codex/app-server) for generating schemas from the installed version. Fixtures establish parser and upload behavior for these shapes; they are not evidence that a live delegation or historical corruption occurred.

Regression tests cover both transports, known/unknown senders, malformed events and wrappers, escaping, mixed content, injected context, normal conversation, incremental capture, cursor migration, replay, retries and chunk metadata. Upload tests mock the memory boundary; test runs should also block `fetch` and use isolated `HONCHO_CONFIG_DIR` and `CODEX_HOME` directories. No fixture test should use a live Honcho workspace.

## Upgrade considerations

Build and review the bundle before replacing an installed copy. Deployment is a separate operation: back up each active bundle and the local queue/cursor state, verify the active hook paths, then replace the selected copies using the existing deployment procedure. The build command alone does not install anything.

Use one bundle version consistently while writeback/flush hooks are running. Older versions do not understand delegation queue entries or the migrated cursor format, so a rollback must account for the saved state and any messages uploaded after the upgrade. Do not reset cursors to force historical backfill or replay already sent queues. Existing Honcho records require a separate, explicitly scoped repair if one is ever needed.
